# 智能路由概览

> 状态：目标设计，尚未在当前 `main` 完整实现。
> 适用范围：仅请求模型为 `auto` 时启用；显式指定模型的行为保持不变。

## 为什么需要智能路由

不同模型在能力、质量、价格和延迟上差异很大。始终调用最强模型通常质量稳定，但成本较高；始终调用低价模型又可能在代码修改、工具调用、长上下文或视觉任务上失败。

智能路由的目标不是“尽量使用便宜模型”，而是按以下顺序做决策：

1. 先保证协议、上下文、视觉、工具和结构化输出兼容；
2. 再保证候选策略的质量接近强模型基线；
3. 最后从合格执行方案中选择预期总成本最低的一项。

第一版的产品目标是：

| 指标 | 默认目标 | 含义 |
|---|---:|---|
| 质量保持率 | 不低于强模型基线的 98% | 按真实任务分布加权，不是单次胜率 |
| 非劣置信度 | 不低于 95% | 有足够证据相信质量达到目标 |
| 业务成本下降 | 预期 20%～30% | 只计算在线业务调用成本 |
| 严重错误率 | 低于 1% | 使用 95% 后验上界判断 |
| 在线额外等待 | 0 | 对照回答和质量评审异步执行 |

## 两种模型请求

显式模型和自动模型是两条不同的产品契约。

```json
{
  "model": "strong-model",
  "messages": [
    {"role": "user", "content": "检查这段迁移脚本是否安全"}
  ]
}
```

上面的请求必须继续调用 `strong-model`。代理可以使用当前已有的视觉增强、重试和统计能力，但不能因为价格、评分或模型健康趋势主动换成其他模型。

```json
{
  "model": "auto",
  "messages": [
    {"role": "user", "content": "检查这段迁移脚本是否安全"}
  ]
}
```

上面的请求才会进入智能路由。由于涉及数据库迁移和安全审查，它可能被高风险规则固定到对应强模型基线。高风险判断必须来自结构化硬信号、上下文规则或高置信度任务判断，单个关键词不能直接触发。

| 行为 | 显式模型 | `model=auto` |
|---|---|---|
| 重新选择主模型 | 否 | 是 |
| 能力硬过滤 | 不用于换模型 | 是 |
| 读取已发布策略 | 否 | 是 |
| 会话模型绑定 | 否 | 有稳定 Session ID 时启用 |
| 动态优化抽样 | 否 | 可选 |
| 同模型重试 | 使用当前能力 | 使用统一尝试预算 |
| 模型切换 | 否 | 仅按策略兜底顺序 |

## 四条设计原则

### 安全约束优先

价格和综合评分不能绕过协议、能力、上下文或高风险门禁。模型不支持图片时，代理不能静默删除图片；模型不支持工具或 JSON Schema 时，也不能删掉这些要求来换取低价。

### 路由对象是执行方案

一次调用可能包含任务判断、视觉证据提取、主模型、重试和模型切换。因此路由对象是完整执行方案，而不只是模型 ID。

### 在线策略不可自我改写

真实流量可以生成评估证据和候选策略，但不能直接改变活动策略。任何候选都必须经过评估、灰度和发布。

### 凭据不持久化

llm-proxy 不管理或保存调用方、Upstream 密钥。任务判断、视觉、主模型、对照回答和质量评审都只使用当前请求携带的协议白名单鉴权头；这些值仅在当前请求衍生的内存上下文或有界内存评估任务中传递，不写入 Profile、数据库、日志或持久化队列。

## 什么不在第一版

- 不跨多个 Upstream 或提供方选择节点；
- 不压缩、总结或截断用户会话；
- 不执行模型生成的任意代码或 Shell 命令；
- 不让管理员自由拼装算法模块；
- 不对真实在线请求做未经评估的探索；
- 不为历史配置提供兼容层，旧 Profile 默认关闭智能路由。
