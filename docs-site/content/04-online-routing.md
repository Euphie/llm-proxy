# 在线路由

> 状态说明：`main` 当前尚未实现 `model=auto`。本章描述目标在线路由链路；显式模型请求仍沿用当前代理链路，不参与智能决策。

在线路由的职责不是“猜一个模型名”，而是把请求转换为不可变的执行计划。计划同时包含模型、上游、视觉处理方式、重试与切换上限，以及生成该决策所依据的策略版本。

![在线路由链路](/diagrams/online-routing.svg)

## 两条入口

| 请求方式 | 当前 `main` | 目标行为 |
| --- | --- | --- |
| `model` 为显式模型名 | 按 profile 代理 | 行为保持不变，不进入动态评估 |
| `model=auto` | 不支持 | 进入智能路由，仅支持规定的三个接口 |

目标版本中，`auto` 只支持：

- Anthropic `POST /v1/messages`
- OpenAI `POST /v1/chat/completions`
- OpenAI `POST /v1/responses`

其他接口收到 `model=auto` 时必须返回明确错误，不能静默映射到默认模型。

## 请求特征

路由器先抽取不可变的 `RequestFeatures`。它只描述请求，不携带可修改的请求体。鉴权信息放在独立的请求级内存上下文中，不进入路由特征、策略或持久化记录。

```go
type RequestFeatures struct {
	Protocol             string
	Route                string
	EstimatedInputTokens int
	HasImages            bool
	NeedsTools           bool
	NeedsJSONSchema      bool
	NeedsStreaming       bool
	SessionBindingKey    string
}
```

上下文长度采用保守估算。目标版本不自动压缩、截断或改写用户上下文；如果候选模型放不下完整请求，应在能力过滤阶段淘汰。

## 任务分析

任务分析分为两层：

1. 本地规则识别工具调用、图片、结构化输出、超长上下文等确定性信号。
2. 必要时调用轻量分析模型补充任务类型、难度和质量要求。

分析模型使用结构化输出、`temperature=0`、最多 256 个输出 token，超时为 2 秒。建议输出如下：

```json
{
  "task_type": "coding",
  "difficulty": "medium",
  "quality_sensitivity": "high",
  "required_capabilities": ["tools", "json_schema"],
  "confidence": 0.91
}
```

如果分析超时、输出非法或置信度低，路由器直接选择强基线模型。分析失败不能阻断业务请求。

## 高风险判断

高风险门禁按固定顺序收敛证据：

1. 先检查协议字段、工具动作、操作类型等可解析的结构化硬信号；
2. 再应用 Profile 声明的上下文规则，判断生产操作、数据库写入或迁移、批量变更、权限与认证等组合场景；
3. 前两层仍无法确定时，才采用任务判断模型的高置信度结构化结论。

关键词只能作为上下文证据，不能单独触发高风险。例如仅出现“迁移”不等于正在执行生产数据库迁移。只有结构化规则明确命中，或任务判断结果达到策略规定的高置信度门槛时，才把请求固定到对应强模型基线，并在不含正文的决策追踪中记录触发信号。价格、评分和动态策略都不能绕过这一门禁。

## 能力硬过滤

能力过滤发生在成本和质量排序之前。任何硬条件不满足，候选模型都不得进入打分。

| 条件 | 过滤依据 | 不满足时 |
| --- | --- | --- |
| 上下文容量 | 保守 token 估算与模型上限 | 淘汰候选 |
| 图片输入 | 原生视觉或可用复合视觉计划 | 淘汰候选 |
| 工具调用 | 模型及上游协议能力 | 淘汰候选 |
| JSON Schema | 模型结构化输出能力 | 淘汰候选 |
| 流式响应 | 上游流式能力 | 淘汰候选 |
| 健康状态 | 近期错误率、熔断状态 | 暂时淘汰 |

只有通过全部硬条件的候选才进入质量估计和成本优化。

## 执行计划

路由器返回不可变执行计划，代理层负责执行：

```json
{
  "profile_id": "default",
  "strategy_version": "20260731-001",
  "model_role": "balanced",
  "upstream_model": "gpt-example",
  "vision_plan": {
    "mode": "native"
  },
  "retry_policy": {
    "same_model_retries": 2,
    "max_model_switches": 1,
    "max_total_attempts": 4
  },
  "route_reason": "meets_tools_and_quality_gate_at_lower_expected_cost"
}
```

`route_reason` 应是可枚举的短代码或低基数字符串，不能写入用户提示词或模型回答。

### 路由器与代理层的边界

| 组件 | 负责 | 不负责 |
| --- | --- | --- |
| Router | 特征分析、能力过滤、计划选择、决策追踪 | 发请求、写响应、执行重试 |
| Proxy | 总超时、上游调用、重试/切换、流式写入 | 临时改变策略或重新打分 |
| Vision | 按计划生成视觉描述 | 自行选择主模型 |

llm-proxy 不保存任何调用方或 Upstream 密钥。任务判断、视觉、主模型、异步对照回答和质量评审都从当前请求的临时鉴权上下文读取协议白名单头：共同允许 `Authorization`、`X-Api-Key`，Anthropic 可另带 `Anthropic-Version`，OpenAI 可另带 `OpenAI-Organization`、`OpenAI-Project`。这些值只在当前请求衍生的内存上下文或有界内存评估任务中传递，不进入执行计划、数据库、日志或持久化队列。

## 失败行为

| 失败点 | 目标行为 |
| --- | --- |
| 任务分析失败 | 使用强基线 |
| 无候选通过能力过滤 | 返回可诊断的能力不匹配错误 |
| 质量或成本统计缺失 | 使用保守先验；必要时选强基线 |
| 策略快照读取失败 | 使用进程内最后一个有效快照 |
| 请求显式指定模型 | 跳过上述智能路由步骤 |

## 验收检查

- [ ] 显式模型请求的行为与当前 `main` 一致。
- [ ] `auto` 仅在三个支持的接口生效。
- [ ] 能力过滤先于质量和成本排序。
- [ ] 高风险判断遵循硬信号、上下文规则、任务判断的顺序，且关键词不能单独触发。
- [ ] 分析失败或低置信度时选择强基线。
- [ ] 执行计划不可变，且记录策略版本。
- [ ] 当前请求的白名单鉴权仅在内存中供各调用阶段使用。
- [ ] 路由日志不包含密钥、提示词或模型回答。
