# 策略生命周期

> 状态说明：当前 `main` 没有版本化策略、灰度部署或自动回滚。目标设计通过不可变快照和显式状态机管理每次路由变更。

策略是一个可审计、可回滚的不可变快照，而不是一组运行时随时变化的参数。在线请求只读取已发布快照；评估器只能创建新版本，不能修改正在使用的版本。

## 策略快照

一个快照至少包含：

```json
{
  "version": "20260731-001",
  "alias": "生产环境-质量优先",
  "profile_id": "default",
  "parent_version": "20260725-002",
  "modules": {
    "task_analyzer": "rules+llm-v1",
    "quality_estimator": "bayesian-v1",
    "cost_estimator": "catalog-runtime-v1",
    "optimizer": "quality-constraint-v1",
    "quality_evaluator": "pairwise-v1",
    "publisher": "snapshot-v1"
  },
  "model_catalog_revision": 18,
  "created_at": "2026-07-31T08:00:00Z"
}
```

规范版本严格使用 `YYYYMMDD-NNN`：八位日期加当天三位递增序号，例如
`20260731-001`。同一日期的序号在 SQLite 事务中分配，并由
`(profile_id, version)` 唯一约束保证并发安全。

快照发布后不可修改。模型目录、阈值或模块版本发生变化，都应创建新版本。管理员可以设置
Profile 内唯一、可修改的别名，但别名只用于界面展示；请求、会话绑定、缓存键、统计与审计
必须始终写规范版本，不能把别名当作策略身份。修改别名不会生成新版本，也不会触发热加载。

## 状态机

| 状态 | 含义 | 允许的下一状态 |
| --- | --- | --- |
| `draft` | 已创建，尚未开始收集证据 | `evaluating`、`failed` |
| `evaluating` | 正在运行离线或在线对照评估 | `ready`、`failed` |
| `ready` | 已通过质量与安全门槛 | `canary`、`failed` |
| `canary` | 少量真实流量验证运行指标 | `active`、`rolled_back` |
| `active` | 当前稳定策略 | `superseded`、`rolled_back` |
| `superseded` | 被新稳定版本替代 | 终态 |
| `failed` | 未通过评估 | 终态 |
| `rolled_back` | 灰度或上线后回滚 | 终态 |

每次状态变化都写入策略事件表，包含操作者、原因、证据摘要和时间。

## 评分与发布门禁

发布先检查硬门禁，评分不能用成本收益抵消质量、安全、协议或能力失败。四个分量均归一化为
`0..100`，综合分固定为：

```text
Score = 0.50 × 质量保持
      + 0.25 × 成本节省
      + 0.15 × 最终成功率
      + 0.10 × 延迟与稳定性
```

分量的归一化阈值属于版本化算法参数，页面同时展示原始指标与综合分。评级规则为：

| 等级 | 判定 | 发布建议 |
|---|---|---|
| A | 通过全部硬门禁且综合分不低于 85 | 推荐发布 |
| B | 通过全部硬门禁且综合分为 70～84 | 可发布，但改善有限 |
| C | 数据量或主要任务覆盖不足 | 继续评估 |
| D | 任一硬门禁失败 | 不可发布 |

无论综合分多高，都不能绕过以下硬门槛：

- 质量相对强基线的概率门槛。
- 分层样本量要求。
- 严重错误率上界。
- 安全与数据治理检查。

价格、参与模型、视觉方案或重试参数变化后，已有评分立即标记为“过期”。过期评分可以留作
审计对照，但不能支持新发布；系统必须基于新快照重新评估并生成新的等级。

## 稳定与灰度部署

```json
{
  "profile_id": "default",
  "revision": 42,
  "stable_version": "20260725-002",
  "canary_version": "20260731-001",
  "canary_percent": 10,
  "assignment_salt": "deployment-42"
}
```

灰度分配使用稳定哈希。存在会话绑定时，以绑定键作为分桶输入，确保同一会话不会在稳定版和灰度版之间跳动；无会话时使用请求级稳定标识。

## 原子发布

发布过程采用 compare-and-swap：

1. 读取当前 deployment `revision`。
2. 验证候选仍为 `ready` 或合法的 `canary`。
3. 写入新 deployment 和事件。
4. 仅当 revision 未变化时原子更新活动指针。
5. 失败时重新读取，不能覆盖其他管理员的发布。

新请求读取新快照；已经开始的请求继续持有旧快照直至结束，不在中途换策略。

## 历史快照缓存

发布新版本后，仍可能有会话绑定旧策略。运行时必须按
`profile_id + canonical_strategy_version` 从数据库加载不可变历史快照，并放入有界内存
缓存；不能只保留当前稳定版和灰度版。别名不参与查找。

历史快照只有在会话过期、回滚或安全升级后且已无引用时才可淘汰。路由决策缓存、运行统计和
审计记录同样携带规范策略版本，确保热加载前后的结果不会混入同一批数据。

## 灰度观察与回滚

灰度期间同时观察：

| 类别 | 指标 |
| --- | --- |
| 质量 | 有效成对结果、严重错误、用户显式失败信号 |
| 成本 | 单请求预期与实际成本、重试和切换成本 |
| 可靠性 | 成功率、超时、流中断、能力不匹配 |
| 性能 | 首 token 延迟、总延迟、队列丢弃 |

达到回滚阈值时，活动指针原子恢复到上一稳定版本，灰度策略转为 `rolled_back`。回滚不删除策略及证据。

## 管理操作

管理界面和 API 应支持：

- 查看版本、父版本、模块版本和状态。
- 查看发布门槛及未满足原因。
- 启动或停止灰度。
- 手动回滚到最近稳定版本。
- 查看每次状态变化和部署事件。

所有写操作都要求 profile 范围的授权和审计记录。

## 验收检查

- [ ] 已发布策略不可修改。
- [ ] 状态转换受到状态机约束。
- [ ] 发布使用 revision CAS，不能丢失并发更新。
- [ ] 灰度对会话保持稳定分桶。
- [ ] 在途请求继续使用其开始时的快照。
- [ ] 回滚保留原策略、证据和审计事件。
- [ ] 版本严格使用 `YYYYMMDD-NNN`，别名仅用于展示。
- [ ] A/B/C/D 评级与 50/25/15/10 综合分可复算，过期评分不会用于发布。
- [ ] 历史会话可以按规范版本加载旧快照，且不会被别名或新策略缓存污染。
