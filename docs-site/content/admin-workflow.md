# 后台操作流程

> [!CURRENT]
> 当前 Profile 编辑页按“概况、连接、模型、智能路由、视觉增强、容错、Agent 配置”组织。保存成功后，新请求立即读取新修订。

## 第一次配置的正确顺序

1. **创建 Profile**：填写名称、slug 和协议。slug 决定调用 URL，也决定永久隔离边界。
2. **保存连接**：配置唯一 Upstream，再用具体模型验证协议、路径和鉴权透传。
3. **建立模型目录**：录入上游真实模型 ID，补齐能力、上下文、最大输出、价格和状态。
4. **验证显式模型**：确认请求中的模型 ID 没有被改写，usage 和错误能正确返回。
5. **配置 Routing Policy**：只有需要 `model=auto` 时才做；先角色，再任务映射、Route、候选和预算。
6. **配置视觉增强**：识图模型可以从目录选择，也可以手动输入上游支持的模型 ID。
7. **配置容错**：根据上游真实错误编写 `overload_rules`，不要只提高重试上限。
8. **生成 Agent 配置**：检查客户端使用的 Profile URL、协议和 Session 传递方式。
9. **验收统计**：各发一条显式模型、`model=auto` 和必要时的图片请求。

## 概况与连接

概况页用于识别 Profile，不承载跨 Profile 继承。连接页只配置一个 Upstream；如果上游后面有多个节点，负载均衡和熔断应在网关完成。

连接验证至少覆盖：

- Profile URL 与协议匹配；
- 上游能识别目录中的真实模型 ID；
- 非流式与流式响应都能完成；
- 4xx、5xx 和传输错误没有被错误包装成成功；
- 后台没有保存临时密钥。

## 模型目录录入清单

| 字段 | 为什么必须准确 | 错误影响 |
| --- | --- | --- |
| 模型 ID | 原样发送给 Upstream，区分大小写 | 上游返回不存在或选错部署 |
| 上下文窗口 | 请求硬门槛与最坏计划 | 大请求在上游才失败 |
| 最大输出 | 预算和能力检查 | 执行计划不可实现 |
| 视觉、工具、结构化输出 | 不可补偿的硬能力 | 候选被误选或误排除 |
| 输入、输出、缓存价格 | 估算完整成本 | 费用未知或预算无法发布 |
| 状态 | 控制新请求资格 | 离线模型仍接流量 |

零价格是有效事实，留空表示未知。更新模型部署时不要直接改旧 ID；新增新 ID、切换引用、验证后再退休旧记录，审计链更清楚。

## Routing Policy 操作顺序

1. 选择参与模型；新增目录模型不会自动加入。
2. 指定任务分析模型和强模型基线，必要时指定评审模型。
3. 检查任务类型与难度是否命中正确 Route。
4. 为每个 Route 设置硬门槛、四项权重和候选证据。
5. 设置 `session_lock_token_threshold`；默认 **100K Token**，可由管理员调整。
6. 设置回答、辅助、总调用、重试、切换、deadline 和最坏费用预算。
7. 检查 Production 与 Shadow；Shadow 不会接在线回答流量。
8. 点击“保存并立即生效”，再用统计页确认新 Policy 版本。

智能生成只产生预览。载入预览后仍要逐项检查，并由管理员保存才会发布。

## 视觉增强操作顺序

启用前先确认回答模型的视觉能力事实。目录模型可从下拉框选择；只有辅助识图、未录入目录的模型可以手动输入精确 ID。

保存后用同一张测试图片验证三种结果：原生视觉直接透传、复合视觉产生识图物理调用、重复请求命中识图缓存。识图成功后还要继续检查主回答，二者是独立阶段。

## 容错操作顺序

`overload_rules` 按顺序匹配。为每条规则确认状态码、可选正文条件、等待方式和 `max_retries`。允许配置的可恢复 HTTP 状态是 `408`、`425`、`429` 和 `500..599`。

Policy 中的 `max_retries_per_target` 只是共同预算上限；没有匹配规则时不会触发同模型重试。演练时要在一条路由轨迹里确认多个回答物理调用，不能用下一条客户端请求代替证据。

## 哪些保存会立即生效

| 保存动作 | 校验与发布结果 |
| --- | --- |
| Profile/连接 | 发布新的 Profile 运行时修订 |
| 模型目录 | 生成目录修订，并重建后续请求的运行时事实 |
| Routing Policy | 校验模型引用、Route、角色和预算后创建新 active 版本 |
| Policy 回滚 | 复制历史内容为新版本，不改写历史记录 |

页面提示修订冲突时，说明其他操作已经先发布。刷新并重新应用变更，不要盲目重复提交。

## 修改现网配置的安全顺序

### 替换一个正在使用的模型

1. 新增新模型事实并标记 `available`；
2. 在 Shadow 中积累或导入先验，并用本地证据验证；
3. 更新角色、Route 和视觉引用；
4. 保存 Policy 并发起新请求验证；
5. 将旧模型改为 `offline`，观察后再 `retired`。

### 修改锁定 Token 阈值

先查看长会话 Cache Read、模型价差和切换失败，再调整 `session_lock_token_threshold`。降低阈值会更早稳定模型，也会更早放弃低价候选；提高阈值则相反。修改只影响后续 Session 判断，不重写已冻结计划。

### 开启自动校准

先保持 `auto_update_policy=false` 观察本地证据和建议。确认样本、回滚流程和告警后再开启；普通变化仍受 10 分钟防抖、两次确认和 6 小时冷却保护。

## 上线前最小验收

- 显式模型请求成功，且没有进入任务分析；
- `model=auto` 显示分类、Route、候选筛选、最终模型和预算；
- 图片请求明确显示原生或复合视觉；
- 一个已配置可恢复错误按规则重试，一个未配置错误不重试；
- 共享 deadline 到期返回 504，并停止后续调用；
- usage 或价格缺失时费用明确标记为未知；
- Agent 配置生成结果不回写临时密钥。
