# 统计与故障排查

> [!CURRENT]
> 先确定失败发生在入口、任务分析、候选筛选、视觉、回答、重试还是客户端提交，再判断配置是否合理。

![一次请求的统计与排障链路](/diagrams/observability-troubleshooting.svg)

## 先确定失败阶段

| 页面 | 回答的问题 | 主要维度 |
| --- | --- | --- |
| 用量统计 | 用了多少 Token、缓存和费用 | Profile、协议、模型、时间 |
| 路由轨迹 | 为什么这样分类、筛选和执行 | Session、请求、Route、候选、调用 |
| 模型表现 | 当前本地证据是否支持在线资格 | 任务类型、难度、风险、视觉方式 |

三个页面口径不同。用量聚合不能替代单请求轨迹，模型表现也不能证明某一次失败发生在哪个阶段。

## 会话与请求的层级

会话卡片以“会话ID：XXX”显示去敏引用。一个会话下可以有多次独立客户端请求；左侧“第 N 次”是请求序号，不是代理重试次数。

每个请求有独立 `request_trace_id`。只有同一请求轨迹中的多个回答物理调用，才是同模型重试或模型切换。客户端收到 504 后重新发送，会产生下一次请求。

## 路由轨迹的阅读顺序

1. **请求进入**：协议、估算 Token、图片、工具、结构化输出和流式模式；
2. **任务分析**：实际分析模型、HTTP 状态、分类、各维度置信度和原因码；
3. **任务判断**：任务类型、难度、风险以及是否来自 Session；
4. **候选筛选**：每个候选的 selected/rejected、Production 和原因；
5. **视觉处理**：native、composite、缓存命中或识图物理调用；
6. **模型回答**：模型、状态、耗时、重试索引和切换索引；
7. **请求结束**：`ClientCommit`、最终状态、共享耗时和费用。

不要只看最终模型。候选排除原因能直接指出能力、资格、证据或预算门槛。

## 请求、尝试和物理调用

| 概念 | 统计单位 |
| --- | --- |
| 客户端请求 | 一条路由轨迹和一个最终状态 |
| 回答尝试 | 首次回答、同模型重试或切换后的回答 |
| 辅助调用 | 任务分析和未命中缓存的视觉调用 |
| 物理调用 | 真正发给 Upstream 的一次请求 |

一次请求的总出站调用 = 辅助调用 + 回答物理调用。识图缓存命中不产生新的视觉物理调用。

## 常见信号

| 信号 | 当前含义 | 下一步 |
| --- | --- | --- |
| `0 / network` | 没有取得有效 HTTP 状态 | 看连接、取消、断流和共享 deadline |
| `504` | 代理共享 deadline 已耗尽 | 汇总分析、视觉、回答和等待时间 |
| 视觉 200、回答失败 | 识图成功但最终回答独立失败 | 查回答调用与重试门槛 |
| 没有视觉调用 | 原生视觉、未启用、无需视觉或缓存命中 | 看视觉方式与缓存标记 |
| Shadow 被排除 | 没有在线资格 | 查本地证据与 Policy，而不是提高权重 |
| 下一条请求成功 | 客户端可能重发 | 比较两个 `request_trace_id` |
| 费用未知 | usage 或任一模型价格缺失 | 查每个物理调用的 usage 与目录事实 |

## 视觉失败排查

先确认回答模型是否原生视觉。复合路径要分别检查缓存、识图调用和回答调用。识图 200 只说明辅助描述生成成功，不代表主请求已经返回客户端。

如果识图调用耗尽大部分共享 deadline，主回答可能直接出现 `0 / network` 或 504；这通常不会进入重试，因为时间门槛已失败。

## 重试失败排查

按以下顺序核对：

1. 错误是否可恢复；
2. 是否命中 `overload_rules`；
3. 规则 `max_retries` 是否还有次数；
4. Policy 是否还有回答、总调用、目标重试和费用票据；
5. deadline 是否还有时间；
6. 是否已经 `ClientCommit`。

轨迹只有一个回答物理调用，说明重试门槛未全部成立。不要仅凭 Policy 上限判断“应该重试”。

## 候选没有切换怎么查

模型切换要求冻结计划中已经存在下一个合格候选。检查它是否因能力、Production、质量、稳定性、严重错误或完整调用图预算被提前排除。

即使下一候选存在，切换票据、回答尝试、总调用、费用、deadline 或提交边界任一不足，也不会执行。

## Debug 日志

以 `LOG_LEVEL=debug` 启动后，用 `request_trace_id` 串联：

```text
routing.debug.classification
routing.debug.candidate
routing.debug.attempt_plan
routing.debug.budget_plan
routing.debug.call
routing.debug.completed
```

Debug 记录结构化判断事实、Token 和费用，不记录请求正文、图片、鉴权信息或完整模型回复。日志和数据库轨迹应使用相同请求引用交叉验证。

## 费用口径

只有所有物理调用返回完整 usage，且所有涉及模型都有必要价格事实时，实际费用才完整已知。任务分析、视觉、回答、重试和切换都属于本次请求成本。

最坏费用是执行前冻结的安全上界，实际已知费用是执行后的观测值。两者不同是正常的，但“未知”不能当作零。
