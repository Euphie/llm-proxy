# 运行边界与上线检查

> [!CURRENT]
> 配置保存后热更新运行时；服务重启不是使连接、模型目录或 Routing Policy 生效的必要步骤。

## 运行时职责分界

| 组件 | 负责 | 不负责 |
| --- | --- | --- |
| 客户端 | Profile URL、协议请求、Session 传递 | 服务端候选筛选 |
| Mesotes | Profile 隔离、路由、视觉、重试、统计 | 网关节点健康和模型托管 |
| Upstream 网关 | 多节点负载均衡、健康检查、熔断、区域与节点故障转移 | 当前 Profile 的 Routing Policy |
| 模型服务 | 实际推理与 usage | 代理的统一请求预算 |

每个 Profile 只连接一个 Upstream。代理内的“模型切换”是同一网关中更换模型 ID；禁止把它解释为跨网关或跨 Profile 故障转移。

## 配置热更新

Profile、模型目录和 Policy 保存通过校验后，运行时协调器发布新修订。新请求立即读取；在途请求保持进入时的快照和预算。

服务重启只用于发布代码、环境变量或容器层变更。为了让数据库配置生效而重启，既没必要，也会掩盖修订冲突或运行时发布错误。

## 并发与一致性

控制面使用期望修订号：

1. 页面读取当前修订；
2. 保存时携带期望值；
3. 服务端在同一事务内比较；
4. 不一致则拒绝覆盖；
5. 成功后创建新修订并通知后续请求。

冲突时刷新并人工合并。不要通过重复提交、重启或直接修改数据库绕过。

## 上线前检查

- Profile slug、协议、URL 和唯一 Upstream 与客户端一致；
- 显式模型和 `model=auto` 分别完成真实请求；
- 目录能力、上下文、价格和状态来自实际部署；
- 强模型基线满足目标任务的硬能力；
- Production 候选有可靠本地证据，Shadow 不接在线回答；
- 视觉、重试、切换和最坏费用能装入统一预算；
- `session_lock_token_threshold` 保持默认 100K，或调整有缓存与费用证据；
- 路由轨迹、物理调用和费用口径可用。

## 显式模型验收

显式模型是连接和协议的最小基线。验证：模型 ID 原样发送、非流式与流式响应正确、错误状态不被吞掉、usage 能解析、统计没有任务分析调用。

显式模型失败时先修复连接、协议或上游部署；不要用 `model=auto` 掩盖基础连接问题。

## model=auto 验收

至少准备简单、复杂、工具、图片和高风险/未知风险样本，确认：

- 分类维度和置信度合理；
- 任务映射命中预期 Route；
- 候选排除原因可解释；
- Shadow 不进入回答计划；
- 强模型基线只在安全回退条件下使用；
- ExecutionPlan 的调用数、deadline 和费用符合 Policy。

## 视觉演练

1. 原生视觉模型应直接回答且没有辅助识图调用；
2. 非视觉回答模型应走复合路径；
3. 重复图片在同一安全作用域可命中缓存；
4. 识图失败不能把识图模型变成回答模型；
5. 识图成功、回答失败要显示两个独立阶段；
6. 上下文不足应在规划阶段排除。

## 重试与超时演练

1. 命中 `overload_rules` 的可恢复 HTTP 错误按规则重试；
2. 没有规则时不因 Policy 上限而重试；
3. 401/403 等硬错误直接返回；
4. 共享 deadline 到期返回 504，且没有后续调用；
5. `ClientCommit` 后断流只记录失败，不产生第二份回答；
6. 计划内下一候选存在且预算允许时才切换。

演练证据必须来自同一 `request_trace_id` 的物理调用，不要把客户端下一次发送算作代理重试。

## Session 与缓存验收

使用真实长会话观察稳定任务数、最低置信度、会话 Token、Cache Read、锁定原因和实际费用。默认 100K 不是所有工作负载的最优值，管理员可以调整，但应保留调整前后证据。

确认新用户任务仍触发风险和硬能力复检；模型退休、Policy 更新或主动升级时，旧锁定不能强行绕过当前事实。

## 自动校准上线顺序

1. 导入固定版本公开评测目录；
2. 保持新候选 Shadow；
3. 开启动态优化但保持 `auto_update_policy=false`；
4. 观察样本、保守区间、严重错误和队列；
5. 验证手动保存、历史和回滚；
6. 再开启自动更新；
7. 监控 10 分钟防抖、两次确认、6 小时冷却和安全降级。

## 安全与数据边界

- 鉴权由调用方透传，后台生成 Agent 配置不保存临时密钥；
- 路由轨迹与 Debug 日志不保存原始提示词、图片或完整回答；
- Session 以不可逆安全引用展示为“会话ID”；
- 视觉缓存使用模型、提示、图片内容和鉴权作用域；
- 路由、评测、执行计划和回退不得离开当前 Profile。

## 变更与回滚

发布模型或 Policy 变更时记录：变更前后修订、模型目录版本、验证请求 ID、Production/Shadow 差异、费用与失败变化、回滚结果。

Policy 回滚会复制历史内容为新版本，并用当前模型目录重新校验。这里不保留旧文档 URL、旧模型名或旧策略格式的兼容层；存在外部依赖时要单独迁移。

## 容器发布检查

代码或内嵌后台帮助发生变化时才需要重建服务。重建后验证：

- 容器使用预期工作树构建；
- 数据目录仍指向正确持久化路径；
- 健康检查与管理后台返回 200；
- restart count 为 0；
- 新帮助脚本和 SVG 资源可访问；
- 至少一条只读或安全测试请求通过。

## 验收证据

> [!EVIDENCE]
> 源码和自动化测试证明控制路径存在；生产验收仍需要真实上游、真实客户端、真实 Session 和实际费用数据。保留请求 ID、Policy 版本、模型目录修订和回滚结果，才能形成可复查证据。
