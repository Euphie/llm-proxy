# 视觉预处理

> [!CURRENT]
> 视觉模型是辅助预处理模型，不是最终回答模型。先选回答候选，再为该候选决定原生或复合视觉路径。

![视觉预处理决策与调用链路](/diagrams/vision-processing-flow.svg)

## 视觉不是最终回答模型

视觉层只把图片转换为可供回答模型使用的事实。即使识图成功，用户要求的推理、编码、总结或决策仍由原回答模型完成。

### 什么时候会发起识图请求

必须同时满足：请求包含受支持图片、Profile 开启视觉预处理、当前回答候选不能原生处理图片，并且执行计划允许复合视觉调用。

以下情况不会发起辅助识图：

- 请求不含图片；
- 回答模型原生支持当前图片请求；
- 视觉预处理未开启；
- 相同作用域的识图缓存命中；
- 辅助调用、总调用、deadline 或最坏费用不足。

## 三种规划结果

| 模式 | 发送给回答模型的内容 | 物理调用 |
| --- | --- | --- |
| `native` | 保留原始图片块 | 只发回答调用 |
| `composite` | 图片替换为带边界的客观描述 | 未命中缓存时先识图，再回答 |
| 不可执行 | 不发起回答 | 候选被排除或请求明确失败 |

识图模型只回答“图片里有什么”。用户要求的推理、编码、总结或决策仍由原回答模型完成。

## 配置识图模型

后台支持两种输入方式：

1. 从当前 Profile 已录入的模型中选择；
2. 手动输入 Upstream 支持的精确模型 ID。

目录选择可以减少 ID 拼写错误，并复用能力与价格事实。手动输入适合仅做辅助识图的部署，但不会自动让该模型参与普通候选评分。

如果配置引用目录模型，运行时要求它确认视觉能力。手动模型仍需由管理员验证上游协议、图片格式、响应结构和费用。

## 提示词边界

识图提示词应要求客观描述：主体、文字、界面状态、布局和与问题相关的视觉事实。不要让识图模型直接执行用户最终任务，否则会出现两套推理链和不可解释的结果。

识图响应必须包含非空文本。解析失败、空文本或不支持的响应结构会记为视觉阶段失败，不会伪造空描述继续回答。

## 支持的协议文档

视觉层复用统一请求文档解析，支持 Messages、Chat Completions 和 Responses 中的图片节点。重写只替换图片块，保留其他消息、工具和协议字段。

每个替换文本带有明确的视觉代理前缀与图片位置边界，避免回答模型把识图描述误认为用户原始文字。

## 识图缓存键

基础缓存键包含：Provider、识图模型、识图提示、图片来源类型和规范化图片载荷。作用域缓存键再通过 HMAC 加入允许透传的鉴权 Header 值。

这意味着：

- 不同 Profile 或鉴权域不会共享敏感视觉结果；
- 改识图模型或提示会自然失效；
- 同一图片在不同任务上下文中的重写仍保留位置边界；
- 缓存存的是描述，不是一次最终回答。

统计里没有视觉物理调用不代表视觉逻辑没运行，可能只是缓存命中。

## 上下文与 Token 预留

复合视觉会为图片描述预留额外上下文。运行时按图片数和描述上限估算，并包含描述包装开销。如果回答模型上下文无法容纳重写后的请求，该候选在规划阶段就应被排除。

视觉调用消耗 `max_auxiliary_calls`、`max_total_outbound_calls`、共享 deadline 和最坏费用。缓存命中省去物理识图调用，但主回答预算不会消失。

## 失败边界

| 失败位置 | 当前行为 |
| --- | --- |
| 图片解析失败 | 在视觉或请求解析阶段明确失败 |
| 识图调用失败 | 记录视觉物理调用和失败，不把识图模型当回答模型 |
| 识图响应无文本 | 视为格式失败，不继续使用空描述 |
| 回答调用失败 | 即使视觉成功，也按回答阶段独立处理 |
| 共享 deadline 到期 | 返回 504，不在过期上下文继续识图或回答 |

只有冻结计划里还有其他可行回答候选，且切换预算允许时，失败后才可能继续。识图成功本身不会增加模型切换权限。

## 排查客户端无响应

1. 确认轨迹选择 `native`、`composite` 还是不可执行；
2. 查看是否有视觉物理调用，或是否记录缓存命中；
3. 检查识图模型、状态、耗时和响应解析；
4. 继续检查主回答物理调用，识图 200 不等于请求成功；
5. `0 / network` 表示没有有效 HTTP 状态；
6. 504 要按分析、视觉和回答累计时间排查；
7. 相邻请求成功通常是客户端重发，不是本次视觉调用自动重试。
