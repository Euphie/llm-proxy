# 管理控制台

管理控制台位于 `/_admin/`。它只管理转发配置、模型事实和运行策略，不保存调用方密钥。

## 首次使用

首次启动使用账号 `admin`、密码 `admin` 登录，并按页面要求设置至少 10 个字符的新密码。随后后台会进入四步引导：

1. **连接上游**：填写名称、Slug、协议和 Upstream 基础地址。
2. **模型（选填）**：只做普通转发时可以跳过；智能路由依赖这里录入的模型。
3. **Agent 配置**：生成 Claude Code、OpenCode、Codex 或通用客户端配置。
4. **验证请求**：从 Agent 发送一个真实请求，后台会自动检测该 Profile 的累计请求数。

引导页不要求填写 API Key。Agent 仍在每次代理请求中发送自己的认证头。

Profile 的代理路径为：

- 默认 Profile：`/v1/...`
- 指定 Profile：`/<slug>/v1/...`

例如 Slug 为 `coding` 时，Anthropic Messages 地址是 `/coding/v1/messages`。

## 页面说明

| 页面 | 用途 |
|---|---|
| 概览 | 查看运行状态、首次接入进度、Profile 路径和请求数 |
| Profiles | 创建、复制、启停、设为默认或删除 Profile |
| 统计 | 分别查看用量、路由轨迹，以及公开评测、本地 Agent 轨迹和五维模型表现 |
| 系统 | 更新模型信息库、查看潜在影响、修改管理员密码和导出 Profile JSON |

每个 Profile 使用独立设置页：

| 分区 | 主要操作 |
|---|---|
| 概况 | 查看代理路径、协议、功能状态和下一步操作 |
| 连接 | 修改名称、Slug、协议、Upstream、启用和默认状态 |
| 模型 | 录入精确模型 ID、上下文、输出上限、能力和价格 |
| 智能路由 | 配置参与模型、模型角色、生产资格、Session 锁定、模型主动升级和调用预算 |
| 视觉增强 | 配置视觉模型、传输、缓存、限制和提示词 |
| 容错 | 配置同一 Upstream 的普通重试规则 |
| Agent 配置 | 为当前协议生成兼容客户端配置 |

切换 Profile 分区时，未保存修改会触发离开确认。

## 功能依赖

- 基础转发只需要有效的连接配置。
- 模型目录是选填项；Agent 配置不依赖模型目录。
- 输入、输出、缓存读取和默认缓存写入价格在后台按美元/百万 Token 填写，路由预算按美元填写；
  API 与数据库仍使用整数微美元。未知模型 ID 可从可搜索的模型库套用参数模板。
- 智能路由必须先录入至少两个不同模型，并选择至少两个参与模型。强模型基线和任务分析模型必须引用已录入的精确 ID，实际调用模型还需要输入和输出价格。
- 公开评测只匹配模型录入时确认并保存的 `canonical_model_id`。修改上游模型 ID 会清空该映射；旧 Profile 不自动迁移，但不影响普通转发。
- 对比学习依赖已启用的智能路由和可用的质量评审模型。
- 模型主动升级依赖至少一次模型切换预算，所有非强基线候选模型还必须明确支持工具调用；低级模型申请后，代理重放原始请求并只返回更强模型的回答。
- 每个 Profile 只配置一个 Upstream；多节点容错由上游网关负责，普通重试可独立配置。
- 视觉增强启用后必须填写视觉模型；和智能路由同时使用时，该模型还需要视觉、价格、上下文和最大输出能力。

后台会在功能入口显示缺失项和直达链接。服务端保存校验仍是最终边界。

模型 ID 区分大小写。模型被路由角色、Route 或视觉配置引用时，后台会阻止删除或改名，并列出需要先处理的引用。关闭智能路由、视觉增强或对比学习只停用运行时行为，不会清空已填写的详细配置。

## 日常操作

1. 从“概览”确认 Profile 已启用并收到请求。
2. 需要接入新客户端时，打开 Profile 的“Agent 配置”。生成内容只保留在浏览器中，真实密钥在 Agent 本地设置。
3. 需要视觉或智能路由时，先补齐“模型”事实，再按页面依赖提示启用功能。
4. 请求异常时打开“统计 → 路由轨迹”查看分类、候选排除原因和调用链；Agent 任务采集与模型质量问题进入“模型表现”。
5. 修改管理员密码或导出配置时进入“系统”。导出文件不包含调用方密钥。

## 更新模型信息库

进入“系统”，在“模型信息库”中查看当前来源、revision、获取日期和模型数，点击
“从 Models.dev 更新”执行一次手动更新。成功后新目录立即用于后台录入建议，无需重启；更新失败则
继续使用旧版本。

更新后页面会扫描全部 Profile 的当前模型目录和不可变 Policy 历史，列出能力下降、容量变化和价格变化的
潜在影响。报告仅供检查，不会修改已保存的 Profile、模型状态或线上 Policy。

## 更新公开评测目录

进入 Profile 的“智能路由”，点击“生成推荐预览”。推荐只填入当前浏览器的本地编辑副本，不写数据库，也不影响
线上请求。检查角色、Route、门槛、权重、任务映射和预算后，点击“保存并立即生效”才会创建一个新的不可变版本。

费用、延迟、每日验证预算及公开评测数据管理位于“高级设置（可选）”。其中“下载并更新公开评测”会显示
LiveBench、BFCL、VLMEvalKit、LMArena 和 SWE-bench 的进度；五个来源全部成功后才切换目录，失败时继续
使用旧版本。目录更新和推荐预览都不会覆盖 Active Policy。公开数据只用于没有本地数据时的冷启动；
可靠的本地路由 Trace 和异步质量评测优先。

页面显示的 Active Policy ID、Runtime revision 和模型目录 revision 就是新请求正在使用的状态。只有请求中的
`model` 为 `auto` 时才按 Active Policy 选模；指定具体模型时仍会检查该模型在当前目录中是否 `available`。
保存前会先验证并预构建完整 Runtime，成功后数据库提交和内存指针原子切换；失败时线上状态完全不变。

“统计 → 模型表现”依次展示公开评测、本地 Agent 评测和本地质量证据。公开评测只负责冷启动；本地 Agent
区域展示完整工具轨迹是否仍在采集、已评测、仅审计或中断。管理员可查看解密后的脱敏轨迹并删除记录，但不能
重新评测历史记录。原始轨迹保存 7 天，上游凭据不会写入数据库。

历史 Policy 永远只读。回滚会按当前 Profile 和模型目录重新校验目标版本；兼容时复制为一个新的 Active 版本，
不兼容时返回 `rollback_incompatible`，不会替换模型或改变 Runtime。

## v25 迁移与恢复

服务首次打开 v24 数据库时，会先在 `data/migration-backups/v25-<UTC>/` 写入一致性 SQLite 备份和旧
`crs2` 策略 ID 16 导出，再迁移规范化模型目录和不可变 Policy。ID 16 的应用结果写入同目录的
`crs2-strategy-16.result.json`；校验失败时保留由原 Active 迁移出的 Policy 并继续启动。

需要恢复时先停止服务并保留故障数据库，再把该目录中的 `llm-proxy-v24.db` 复制为数据目录的
`llm-proxy.db`，最后使用旧版本程序启动。v25 删除了旧策略生命周期表和 Profile v1 路由字段，不能把
v25 数据库直接交给旧版本运行。
