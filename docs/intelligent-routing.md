# 智能路由设计

> 状态：Phase 1 智能路由运行时已实现。当前包括首轮任务判断、Session 连续性、每轮硬规则、模型主动升级、
> 视觉增强、同一 Upstream 重试、异步对比学习、不可变策略发布，以及完整调用预算和成本核算。

智能路由只在客户端明确发送 `model=auto` 时生效。它先判断任务需要什么能力，再在当前
Profile 中先排除能力、质量、稳定性或严重错误门槛不合格的模型，再按四维加权路由分选择候选。客户端指定具体模型时，代理保持原有
行为，不参与选型。

## 一分钟了解

```text
首次请求（没有 Session 绑定）
  → 每轮风险与硬能力检查
  → 调用轻量任务分析模型，提取任务类型、复杂度信号、风险和三类置信度
  → 任务类型映射 Route
  → 先按能力、质量、稳定性和严重错误率过滤，再按质量、稳定性、成本效率和性能加权选型
  → 低级模型回答前可通过内部工具申请升级
  → 成功模型写入 Session 绑定

后续追问（携带同一个有效 Session ID）
  → 尚未到强模型基线时，仍分析本轮任务以发现升级需要
  → 已绑定强模型基线时，跳过任务分析，直接继续使用最高模型
  → 仍检查最高模型是否满足图片、工具、上下文和结构化输出等硬能力
  → 当前模型若发现任务明显超出能力，在输出正文前调用内部升级工具
  → 代理丢弃该次未完成输出，用冻结计划中的更强模型重放原始请求
  → 未申请升级时正常回答；升级成功后更新 Session 绑定
```

最重要的边界是：**一次请求只能使用 URL 选中的 Profile**。模型选择、视觉识别、重试、
容错和异步评测都不能跨到其他 Profile。

首轮选中的低级模型同样可以注入升级工具，作为任务分析之后的第二层质量保护。Claude Code 和
Codex 的原生会话标识会被自动识别；其他调用方需持续发送相同的 `X-LLM-Proxy-Session-ID`，系统
才能区分首次请求和后续追问。没有有效 Session 时，每次请求都按首次请求处理。

贝叶斯更新不在上述在线链路中执行。它位于异步学习支路：抽样比较候选模型与强模型基线，累计
评审证据并计算保守后验区间，达到可靠样本后生成新的 Policy 推荐预览。只有管理员检查并执行
“保存并立即生效”后，新指标才会影响后续在线选模。

## 1. Profile 中需要配置什么

启用智能路由的 Profile 必须配置：

- 至少录入两个不同模型，并选择至少两个参与路由的模型；新录入的模型不会自动加入。
- 一个强模型基线：任务无法可靠判断或没有更合适候选时使用。
- 一个轻量任务分析模型：首次请求和尚未绑定强模型基线的后续请求会调用。
- 一份固定的语义风险分类契约：任务分析模型按当前意图、上下文和实际操作判断。
- 一份有效 Active Policy：包含角色、任务类型到 Route 的映射、默认 Route、各 Route 的候选、硬门槛、
  四项权重和统一请求预算。每次成功保存都会创建不可变版本并立即成为 Active。

以下能力按需配置：

- 开启视觉增强时必须指定视觉模型。
- 开启动态策略优化时必须指定质量评审模型、抽样比例和每日预算。
- 开启模型主动升级时，策略必须允许至少一次模型切换，且所有会承接回答的非强基线候选模型必须明确支持工具调用。
- 同一 Upstream 重试和模型切换由策略中的尝试预算统一限制。

缺少对应的必填角色时，配置不能发布。未开启视觉增强或动态策略优化时，不会发起相关的
辅助请求。

## 2. 模型与 Upstream

系统把“模型是什么”和“请求发到哪里”分开：

- **ModelCard** 描述模型能力和成本，例如上下文窗口、最大输出、是否支持视觉、输入与输出
  单价。
- **Upstream** 是当前 Profile 唯一配置的上游网关地址。

缺失数据按保守规则处理：未登记或未确认的能力不视为满足对应硬约束；任何在已启用功能中
可能被调用的模型，如果缺少计算完整成本所需的价格字段，配置或策略不能发布。价格为零是
有效值，字段缺失才表示未知。

显式模型和 `model=auto` 的全部任务分析、视觉、回答、重试与模型切换都使用同一个 Upstream。
执行计划不会保存或选择第二个地址。多节点负载均衡、健康检查、熔断和节点故障转移由该地址后的
上游网关负责，代理不推断网关内部部署，也不转换请求、协议或凭据。

`provider_id`、`credential_scope`、`targets` 和 `max_target_switches` 已删除且不提供兼容层。
旧存储值读取时丢弃，管理 API 的严格写入会拒绝这些未知字段。

## 3. 在线路由

v1 的 `model=auto` 只支持可完整解析的推理操作：Anthropic `POST /v1/messages`，以及 OpenAI
`POST /v1/chat/completions`、`POST /v1/responses`。其他方法或路径使用 `auto` 时返回明确的
unsupported operation 错误；显式模型仍保持现有透传行为，不被 Session 或智能路由改写。

入口路径决定唯一操作，解析器不会根据正文里是否碰巧出现 `messages` 或 `input` 字段来猜协议。
图片、任务文本和实际工具操作都由这份操作感知文档模型读取；协议字段之外的同名嵌套对象不参与
图片计数、能力过滤、风险判断或改写。Responses 的字符串 `input`、easy-message 字符串
`content` 和直接 `input_text` 都用于任务分析与输入 Token 估算。任务分析读取最近最多 8192 个字符的
用户对话上下文，并按语义判断任务难度和风险，避免历史操作脱离当前意图污染后续请求。

在线请求按固定顺序处理：

1. URL 先选定唯一 Profile，并加载一次不可变的运行时快照。
2. 协议、安全和请求结构先做入口预检；模型能力、上下文长度等形成后续候选硬约束。
3. 首次请求调用轻量任务分析模型；同一用户任务产生的工具回合复用原判断。不同任务连续 3 次选择
   同一模型、最低置信度达到 85%，且会话消息或当前响应缓存读取达到配置阈值后锁定模型；默认阈值为 100K Token。
   新用户任务即使已有锁也会重新分析风险，普通风险才保留锁定模型。system、Skill 与工具定义不计入。
   最高模型成功回答后立即锁定，包括任务分析选中、
   安全回退选中和模型主动升级三种来源。
4. 任务类型按已发布策略映射到一个 Route；没有匹配时使用默认 Route。策略变化或绑定失效后重新判断一次。
5. 高风险请求直接使用满足要求的强模型基线；明确的能力要求用于过滤候选。
6. 其余请求先应用当前 Route 的能力、质量、稳定性和严重错误门槛，再选择四维加权路由分最高的模型。
7. 系统规划视觉处理、同一 Upstream 重试与模型切换，并生成不可变的 `ExecutionPlan`。
8. 执行器只能按这份计划工作，不能在执行中临时增加调用。

因此，轻量任务分析负责在会话到达强模型基线前判断 Route、难度和语义风险，Session 负责保证模型质量
只升不降；强模型基线是该策略内的吸收状态，后续请求直接复用。模型主动升级负责解决低级模型执行后才发现能力不足的情况。

轻量任务分析通过普通工具返回任务类型、复杂度信号、风险以及任务类型/复杂度/风险三类置信度；
没有强制 `tool_choice`，文本 JSON 仅作为协议能力不足时的回退输出。分析超时、网络故障、过载或
畸形输出时整体回退；任务类型置信度不足时走默认 Route，复杂度置信度不足时至少按中等任务保护，
风险置信度不足时风险记为 `unknown` 并使用强模型兜底。分析回退和风险未知不会冒充高风险，也不会进入异步评测。
只有请求预算和 deadline 仍允许、且当前 Profile 的
强模型基线满足全部硬约束时才会回退；否则请求失败。任务分析遇到 401/403、不可重试 4xx 或重定向/
协议响应属于硬失败，不能回退到强模型基线。
调试日志只记录失败阶段、状态码和响应大小，不包含上游响应正文。

### 任务分类和难度派生

任务类型固定为 `simple`、`general`、`reasoning`、`math`、`coding`、`tool_use`、`vision`。
重叠时按主要交付物判断：截图辅助修代码仍是 `coding`，代码实现数学证明但证明是主要目标时是
`math`，外部系统编排本身是主要目标时才是 `tool_use`。策略不能配置这七类之外的任务类型。

分析模型不直接输出 `easy/medium/hard`，而是提取解法是否明显、改动是否局部、步骤是否有限、
形式化证明、多约束相互影响、分布式或并发、原因未知或非确定性、跨系统、不变量或兼容性、
安全关键、定量 SLO、广泛验证、迁移或回滚等布尔信号。后端用固定规则派生难度，因此更换分析模型
不会改变难度定义。只有“修改这个 bug”之类信息不足的请求会标记 `underspecified`，按中等任务处理
并降低复杂度置信度，不会凭空推断为困难。

### 高风险任务怎么判断

高风险首先由轻量任务分析模型结合最新用户意图、近期上下文和实际或强制工具操作做语义判断。判断
覆盖多语言、标点、空格、词形、同义表达和轻度混淆，并区分实际执行意图与引用、否定、历史讨论、
只读解释、审计或沙箱演练。典型范围包括生产数据破坏、部署与基础设施变更、凭据和权限、资金操作、
敏感数据处理、安全攻击与绕过，以及安全关键系统操作。

结构化输出、长上下文、图片和普通 Shell/Edit 操作只形成能力或容量约束，本身不等于高风险。
分析模型给出高置信高风险结论后只使用满足全部硬约束的强模型基线；强基线不满足时明确失败。

会话历史中的 `shell_exec`、`edit` 或旧工具调用只作为任务上下文，不会让后续普通追问自动升级。
如果当前请求明确要求执行生产删除、凭据轮换、支付或数据库写入等敏感操作，分析模型会将其判为高风险。

Anthropic 只从 assistant `tool_use` 和命名 `tool_choice` 提取实际操作；Chat Completions 只从
assistant `tool_calls[].function.name` 和命名 `tool_choice` 提取；Responses 只从 `function_call`
输入项和命名 `tool_choice` 提取。操作名有数量、长度与去重边界，只进入当次内存中的分析事实，
不会把任务文本或工具参数写入路由轨迹。

输入 Token 仍采用约四字节一 Token，但基于同一文档生成的 canonical JSON envelope。仅协议图片
块内的 Anthropic base64 `source.data` 或 OpenAI data URL base64 payload 会替换为短标记；周边
JSON、用户文本、工具 schema、普通 URL/`file_id` 和协议位置外的相似字段仍完整计入估算。

**行为变更：**高风险策略按 v2 语义执行，不再兼容旧版“工具、结构化输出或长上下文天然高风险”
的宽泛判断，也不再提供文本或工具名关键词匹配。

## 4. 视觉增强

系统先选主模型，再决定图片如何处理：

- 主模型支持视觉：图片直接交给主模型。
- 主模型不支持视觉，但 Profile 已开启视觉增强：视觉模型先生成与当前问题相关的图片描述，
  主模型再基于描述回答。
- 两者都不满足：该主模型不能成为候选。

视觉识别属于本次 `ExecutionPlan` 中的辅助调用，共享同一个截止时间、取消信号和调用预算。
缓存必须同时区分 Profile、图片内容、视觉模型、传输方式、视觉提示词、图片所在问题的上下文
以及鉴权域，避免旧描述或其他调用方的结果污染当前回答。

跨请求缓存合并采用不可变 owner：创建物理视觉调用的请求 context 控制其取消和计费，waiter
不能延长或接管该调用。owner 取消后，旧调用必须退出并记到旧 owner；仍存活的 waiter 重新竞选，
使用自己的预留和 trace 发起替代调用。取消 waiter 不影响存活 owner，成功共享和后续缓存命中
不消费视觉票据。缓存键和值仍只按内容作用域共享，不加入请求 trace。

视觉模型启用时必须明确支持视觉，同时具备上下文窗口和最大输出能力；配置的描述输出与单图
提示预留必须能放入该窗口。图片来源还必须能被配置的视觉传输承载：OpenAI Chat 传输不支持
`file_id`。影子请求保留 Upstream 的基础路径和查询参数，但把末尾推理路径规范为配置的
`/v1/messages`、`/v1/chat/completions` 或 `/v1/responses`，请求体也按该传输重新构造。
规划器按每图 `4 × max_tokens` 字节加固定封装开销预留主模型输入；视觉描述超过同一字节上限时
按畸形响应处理并进入既有视觉回退，避免实际上游突破冻结计划。

复合模式在主回答发出前遇到连接失败、超时、临时过载或畸形视觉响应时，可在剩余预算内重试
同一 Upstream，再切换计划内模型并重新执行其视觉步骤；401/403、能力/请求协议错误及不可重试
4xx 是硬失败。显式模型不进入智能模型回退。

## 5. 重试、切换与提交边界

当前在线请求的所有上游调用共用一份 `AttemptBudget`：

| 字段 | 含义 |
| --- | --- |
| `max_answer_attempts` | 主回答最多尝试次数 |
| `max_auxiliary_calls` | 任务分析、视觉等辅助调用上限 |
| `max_total_outbound_calls` | 所有上游调用总上限 |
| `max_retries_per_target` | 同一 Upstream 的重试上限 |
| `max_model_switches` | 主模型切换上限 |
| `deadline` | 整个请求的截止时间 |
| `max_worst_case_cost` | 最坏情况下允许的费用上限 |

请求级预算在路由开始前创建；在线任务分析先消耗预算，随后生成的 `ExecutionPlan` 固定剩余
预算和每个模型的执行顺序。可重试故障只会再次调用同一 Upstream，重试耗尽后才尝试计划内的
下一个模型；每次视觉、回答、重试或切换都必须先占用预算。重试循环结束后
不得再额外发送一次请求。代理自身的请求预算截止且客户端连接仍有效时返回明确的 `504`；客户端
已经取消连接时不再尝试写响应。

容错规则只接受 `408`、`425`、`429` 和 `500..599`。`401/403`、其他不可重试 4xx 及重定向/
协议错误是硬失败，不能重试或切换模型。容错规则只决定是否等待并重试同一 Upstream；
上述可重试 HTTP 状态即使没有命中规则，也会在 `ClientCommit` 前沿冻结计划切换模型。
流式响应出现第一个完整、合法且与入口操作一致的成功事件后进入 `ClientCommit`；Anthropic
首事件必须是含 `message` 对象的 `message_start`，Chat Completions 首 chunk 必须是含非空
`choices` 数组的 `chat.completion.chunk`，Responses 首事件必须是含 `response` 对象的
`response.created` 或 `response.queued`。heartbeat/comment 不提交，错误或跨协议事件、任意 JSON 与提交前的孤立
`[DONE]` 均视为硬协议失败并终止，不能向客户端泄露预提交字节；只有提交前的连接、EOF 或读取
失败等可恢复传输故障才能沿冻结计划回退。提交后即使上游失败，也不能再换模型或重试，以免向
客户端拼接两份响应。响应后的异步评测使用独立评测预算，不占用已经结束的在线请求预算。

任务分析完成后，规划器按剩余预算冻结路径感知的最坏调用图，展开可达的模型、逐图视觉
调用和重试边。复合节点必须先原子预留视觉与首个回答容量，才允许视觉请求上网；缓存命中和未执行
分支释放未使用容量。每次真实网络调用只消费一张票据，失败调用同样计数，缓存或共享命中不计调用。
每个显式和 `model=auto` 请求都会生成一个不透明随机 trace ID；auto 请求同时把它作为调用账本
correlation ID。每次物理视觉加载另有一个 call ID，owner 和 waiter 日志共享该 call ID 与
owner trace ID。这些 ID 只用于代理内部关联，不包含请求内容或凭据，也不转发给 Upstream；
安全随机源不可用时请求会失败，不回退到可预测 ID。

## 6. Session 固定模型

Session 绑定只对 `model=auto` 生效，不能覆盖调用方显式指定的模型。同一 auto 会话优先沿用
已经选择的模型，减少回答风格、工具能力和缓存前缀频繁变化。会话键使用 HMAC 生成，原始 Session ID
和 Profile 参与摘要；Route 不参与键，调用方鉴权域参与隔离。数据库不保存原始
Session ID 或凭据。绑定保存任务指纹、任务类型、难度、Route、模型、最低质量、稳定计数、锁定状态和策略版本。Claude Code 的
`X-Claude-Code-Session-Id` 与 Codex 的 `Session-Id`（`Thread-Id` 作为后备）会被自动识别；其他
客户端可通过 `X-LLM-Proxy-Session-ID` 提供稳定标识，代理在转发前移除该自定义内部头。请求缺少
有效 Session ID 或受支持鉴权头时，不建立跨请求绑定。TTL 默认 `24h`，可在 Profile 中设置
`5m` 到 `720h`。

- 同一用户任务的工具回合复用分类和模型；只有新的用户任务才会推进预热计数。
- 普通模型锁要求连续 3 个不同任务选择同一模型、最低分类置信度达到 85%，并且会话消息或当前响应实际缓存读取
  达到 `session_lock_token_threshold`；默认值为 100K Token。system、Skill、工具说明等固定前缀不计入。
- 同一任务工具回合跳过重复分析；新的用户任务重新分析语义风险。普通风险保留锁定模型，高风险、风险未知或
  能力不满足时使用强模型基线。升级到最高模型后转为最高模型锁。
- 分类器失败时使用强模型安全回退；只有强模型成功回答才写入最高模型锁，失败请求不会锁定会话。
- 每轮仍检查图片、工具、上下文和结构化输出等硬能力；最高模型不能承载请求时明确失败，不自动降级。
- `429`、`5xx` 或临时 Upstream 故障只影响当前请求，不改变会话绑定。
- 系统不会自动把会话降回较弱模型。

升级后的新模型会成为该 Session 的后续绑定。升级会切换模型缓存，但不会清空其他模型自己的缓存；
没有升级时，同一会话继续使用原模型，更容易保持前缀缓存稳定。发布新策略后，普通未锁定绑定按新 Runtime
刷新。仅修改锁定 Token 阈值时清理普通锁，最高模型锁保留；模型目录变化仍会使不兼容绑定失效。

## 7. 模型主动升级

开启后，代理会为计划中仍有更强候选的低级模型加入一个协议原生的内部工具。模型只有在明显无法
可靠完成任务时才能把该工具作为第一个输出调用。代理会拦截调用并执行以下动作：

1. 丢弃低级模型的内部工具调用和未完成输出；
2. 按冻结计划选择质量更高的下一个模型；
3. 把客户端的原始请求重新发送给新模型；
4. 只把新模型的回答返回客户端。

强模型不会看到低级模型的回答、升级原因或内部工具。Anthropic Messages、OpenAI Chat Completions
和 OpenAI Responses 均使用各自的原生工具格式。调用方禁用工具、强制指定其他工具，或使用了同名
工具时，代理不会覆盖调用方控制，也不会启用本次主动升级。没有更强候选、功能关闭或注入失败时，
不会为此发送额外请求。

主动升级必须发生在任何回答文本之前。流式响应会在提交客户端前识别内部工具；提交后只解析 SSE
事件中的结构化工具调用字段，普通可见文本即使提到内部工具名也会正常转发。上游如果在已经输出
文本后才真正调用它，代理按协议错误终止并隐藏工具内容，不能再把两份回答拼接到同一响应。

内部系统提示和工具定义会成为低级模型请求前缀的一部分；配置不变时该前缀保持稳定。真正升级时
会改用另一个模型，因此该次请求不会继续复用原模型的提示缓存，这是质量保护所需的明确成本。

Session 预热阶段会对新的用户任务执行轻量任务分析；模型主动升级是回答阶段的第二层保护，用于发现分析阶段
仍然低估了任务、或者普通模型锁定后才暴露的能力缺口。普通模型锁定后不再分析，但仍注入升级工具；
最高模型锁定后不再分析，也不再注入升级工具。

如果模型调用了升级工具，但冻结计划中没有可用的更强模型或预算已经耗尽，请求会明确失败，不会把
低级模型未完成的输出当作正常答案返回。

## 8. 质量、成本与选型

Route 是策略中的任务类别，例如简单问答、代码修改或长文分析。一个 Profile 同时只有一个
active 策略，该策略包含多个 Route 和一个必填的默认 Route。每个 Route 分别配置质量目标和
硬门槛，不使用一个全局固定百分比。文档提供“质量优先”“均衡”“成本优先”的建议权重，控制台
由管理员直接填写具体值。

管理员在 Route 候选中填写质量、稳定性、严重错误率和预期延迟，运行时把它们作为发布时已确认的策略事实。开启
动态策略优化后，系统按 Route、任务类型、候选、强基线和评审模型累计胜负、严重错误、成本与
延迟。质量和稳定性估计以配置事实作为先验，旧评审数据按 30 天半衰期衰减，并使用单侧 95% 保守区间；
评审与线上执行样本都达到 20 后才允许生成学习候选。

质量、稳定性和严重错误率都是硬门槛，不能被低价格或综合分抵消。在通过硬门槛的候选里，按
Route 配置的质量、稳定性、成本效率和性能权重计算路由分，分数最高者优先。
普通候选的质量证据不足时使用保守先验；置信下界仍未达到 Route 门槛就排除该候选。没有候选
通过时，只能回退到满足硬约束的强模型基线，否则请求失败。

完整成本包括任务分析、主回答、视觉识别、预期重试、失败后切回强基线，以及按采样率摊销的对比回答和评审调用。
后台使用美元小数输入和展示，
保存及计算时转换为整数微美元，避免浮点累计误差。控制台为每个策略版本展示 Route 原始指标、综合分和 A/B/C/D 等级，便于
比较；等级只用于展示，不能绕过任何质量门槛。

### 后台 Route 配置速查

可以把策略理解成下面这条固定流程：

```text
任务类型 → 映射 Route → 检查能力 → 检查质量、稳定性和严重错误门槛 → 计算四维加权路由分
```

| 字段 | 用途 | 是否影响选模 |
|---|---|---|
| 策略名称 | 策略的唯一版本号，格式为 `YYYYMMDD-NNN`；保存后不可原地修改 | 用于固定和追踪策略版本 |
| 策略别名 | 便于管理员识别，例如“日常均衡” | 否 |
| 默认 Route | 任务类型没有显式映射时使用的兜底 Route | 是 |
| 最低净节省 | 计入已产生费用、预期重试、基线回退和抽样评测后，非基线候选必须达到的最低节省比例 | 是，硬门槛 |
| 候选延迟上限 | 非基线候选延迟必须已知且不超过该值；0 表示不限制 | 是，硬门槛 |
| Route ID | 策略内唯一的内部标识，供任务映射引用 | 间接影响 |
| 最低质量 | 候选质量估计必须大于或等于该值 | 是，硬门槛 |
| 最低稳定性 | 候选稳定性估计必须大于或等于该值 | 是，硬门槛 |
| 最大严重错误率 | 候选严重错误率必须小于或等于该值 | 是，硬门槛 |
| 四项权重 | 质量、稳定性、成本效率和性能权重，总和必须为 100% | 是，决定路由分 |
| 候选模型 | 可以承接该 Route 的参与模型 | 是 |
| 当前质量估计 | 模型在当前 Route 下的初始质量事实，不是全局模型评分 | 是，与最低质量比较 |
| 当前稳定性估计 | 模型在当前 Route 下的稳定性先验 | 是，与最低稳定性比较并参与路由分 |
| 当前严重错误率 | 模型在当前 Route 下的初始严重错误事实 | 是，与上限比较 |
| 预期延迟 | 候选回答端到端延迟；0 表示未知并按 0 分计算 | 是，转换为性能分 |
| 任务类型 | 固定七类之一，由轻量任务分析模型按主要交付物返回 | 是 |
| 难度 | 分析模型提取复杂度信号，后端固定规则派生 | 是 |
| 任务映射 Route | 将任务类型指向某个 Route | 是 |

例如 `simple` Route 的最低质量为 `90%`、最低稳定性为 `90%`、最大严重错误率为 `1%`，其中：

- `fast` 的质量为 `92%`、稳定性为 `93%`、严重错误率为 `0.5%`；
- `strong` 的质量为 `99%`、稳定性为 `99%`、严重错误率为 `0.1%`。

两个候选都通过硬门槛，运行时会选择四维路由分更高的模型；如果 `fast` 的质量改为 `89%`、
稳定性改为 `85%` 或严重错误率改为 `1.2%`，它会先被排除，不再参与加权比较。所有普通候选都未通过时，系统只会
尝试满足请求硬能力约束的强模型基线；强基线也不满足时明确失败。

质量、稳定性、严重错误率和预期延迟是当前 Policy 的初始事实。动态策略优化不会直接修改 Active；它累计异步
评测证据后只能生成本地推荐预览，由管理员确认并保存后立即生效。

### 智能生成 Policy 预览

后台“配置策略”提供“智能生成”和“手动设置”两种方式。智能生成可以根据参与模型、优化目标、
单请求成本上限、延迟目标和每日评测预算生成完整 Policy 预览；生成后可继续手动调整。
新建 Profile 的分步向导会在连接和模型配置保存后提供智能路由推荐。点击“生成推荐并开始编辑”
会在当前步骤直接打开 Route、门槛、权重、映射和预算字段；结果只存在于浏览器，保存前不会影响线上。
已启用智能路由的 Profile 保留现有参与模型、强基线、分析模型和评审模型；未启用的 Profile 只把
初始化建议填入尚未保存的表单。生成器按 easy、medium、hard 难度创建精确任务映射，并覆盖 `simple`、
`general`、`reasoning`、`math`、`coding`、`tool_use` 和 `vision` 标准任务类型。hard、未知难度和高风险请求
始终由强基线硬规则保护。

公共评测目录只提供零本地数据时的领域质量先验和 Shadow 候选排序，不能直接授权生产流量。没有可靠本地证据时，
候选的稳定性和严重错误率按最保守值处理并回退强基线。每次完整生成只更新本地预览，不会自动发布或改写已有版本；
管理员可继续编辑，并在确认后一次保存完整 Policy。目录格式和五类导入方式见
[公共模型评测目录导入](evaluation-catalog-import.md)。

公开评测不能代替异步评测：它不了解当前 Upstream、提示词、工具、Scaffold、延迟、错误率和真实流量分布。
在本地 Evidence 为空时，它只提供最多 20 个等效样本的冷启动先验；本地可靠 Trace 和异步质量证据始终优先。
Profile 模型必须保存精确 `canonical_model_id` 才能匹配公开结果。模型录入时，唯一精确匹配或管理员明确选择
模板会保存该字段；修改上游模型 ID 会清空它。系统不做 Claude 4 → Claude 5 一类家族或跨版本外推。

旧 Profile 不自动迁移该字段：转发仍可工作，但需要在模型页重新确认模板并保存，才会获得公开评测覆盖。
点击“下载并更新公开评测”只更新目录；管理员之后仍需主动点击“生成推荐并开始编辑”，检查并修改 Route、
门槛、权重、任务映射和预算。

缓存价格采用双轨计算：候选排序使用最近 30 天同一 Profile、逻辑模型的真实缓存比例；当前
Session 继续使用已绑定模型时按历史缓存读取/写入比例估算，切换到其他模型时按冷缓存写入估算。
没有有效样本或缓存价格不完整时，预计成本按普通输入计算。硬预算不假设命中缓存，全部预计输入
按普通输入价与默认缓存写入价的较高者预留，避免首次写缓存反而更贵时低估上限。模型切换因此既
考虑质量，也会显式承担缓存变冷的成本。

路由轨迹分别保存计划最坏费用、已发生调用的估算费用、尚未释放的持有容量和 usage 可核算的
已知实际费用。Anthropic 的普通输入、缓存读取、缓存写入和输出分别计价；OpenAI 的输入总数先
扣除已报告的缓存读取/写入 Token，再计算普通输入，避免重复收费。只有所有物理调用都返回完整
usage，且实际使用的价格均已配置时，
才把整条轨迹标记为“实际费用完整已知”；否则保留逐调用估算，并明确显示实际费用未知或仅部分已知。
显式零价格可得到已知零费用。数据库不保存用于核算的请求或响应正文。

## 9. 动态策略优化

动态策略优化默认关闭。管理员配置的抽样比例是上限，不是固定实际比例：当前分桶没有可靠本地证据时
保持上限；有效样本达到 20 后降到上限的 1/2，达到 100 后降到 1/4；近期严重错误或跨日结论冲突时
恢复上限。这个判断只读取本地 Evidence，不读取公共榜单。证据查询和第二阶段抽样都在异步 worker
执行，不阻塞在线请求。评测同时受每日预算限制：

1. 普通无工具请求仍按抽样策略进入异步评测。包含工具调用的 Agent 请求改为完整轨迹评测：必须
   收到真实工具结果和最终回答，且任务为低风险、单模型、内容未截断，才进入有界内存队列。
   队列满、预算不足或任务过期时直接跳过，不阻塞在线请求。
2. 系统比较低成本候选和强模型基线，先做结构化输出等确定性检查，再随机交换 A/B 顺序并交给
   质量评审模型；评审请求不包含模型 ID。
3. 数据库按任务类型、难度、风险和视觉方式分桶，累计五维胜负、严重错误、成本、延迟和预算。
   普通抽样不保存问题、图片或回答；Agent 工具任务会保存经脱敏、加密的完整轨迹 7 天，但始终不保存凭据。
   五维是正确性 40%、完整性 20%、指令遵循 20%、格式与工具安全
   10%、任务完成度 10%。回答和评审
   响应能返回完整 usage 时，证据成本使用含缓存读写的实际费用；否则保留预留成本。每日预算按
   Profile 单独持久化；队列和运行中凭据只存在内存，重启后允许丢失。
4. 如果本次低级模型主动申请升级，异步比较判断它是“有效升级”还是“无效升级”；如果它没有申请
   但强模型明显更好，则记为“漏升”。
5. 未开启 `auto_update_policy` 时，证据只用于后台展示和人工生成预览。开启后，可靠本地证据通过 Route 门槛的
   Shadow 候选需经过 6 小时冷却和两个一致证据窗口才可获得生产资格；证据缺失、不可靠或跌破门槛会立即撤销
   生产资格。在线 Trace、异步评测完成和 30 分钟周期审计驱动同一状态机；每次变化仍创建不可变 Policy 版本，
   上一版本可作为回滚点。

### 贝叶斯算法体现在哪里

贝叶斯算法只用于把异步评测证据转换成保守的策略指标，不参与当前请求的实时选模：

```text
管理员填写的质量、稳定性和严重错误率
  → 作为强度为 20 个等效样本的 Beta 先验
  → 五个维度分别记录候选胜、强基线胜或平局
  → 每个维度独立做 Beta 更新，候选胜和平局都记为“非劣”，强基线胜记为失败
  → 严重错误和非严重错误分别累计
  → 线上请求累计成功率、输出有效率、干净完成率和平均延迟
  → 历史证据按 30 天半衰期衰减
  → 汇总质量与稳定性后验下界、严重错误率后验上界和预期延迟
  → 评审与线上有效样本都达到可靠门槛后形成保守候选指标
  → 手动模式生成预览；自动模式按确认和冷却规则更新生产资格
```

质量和稳定性采用后验均值的单侧 95% 下界，严重错误率采用单侧 95% 上界：样本越少，结果越保守。
“升级准确率”和“漏升率”目前是时间衰减后的观测比例，不参与这两个 Beta 后验。系统也不会用
Thompson Sampling 或在线 Bandit 在请求过程中探索模型；在线路由始终只读取已经发布的不可变策略。

![异步评测与贝叶斯学习流程](../internal/admin/ui/static/intelligent-routing-learning-flow.svg)

系统不配置、不引用也不持久化任何上游密钥。在线主请求、任务分析、视觉和异步评测都只使用
当前请求透传的凭据。异步评测最多在内存保留凭据 10 分钟；进程重启后未完成任务允许丢失。
普通抽样的完整提示词、图片和完整回答不能写入数据库；Agent 工具任务的已脱敏完整轨迹使用
`DATA_DIR/agent-trajectory.key` 加密后保存 7 天，密钥权限为 `0600`。关闭功能或缺少所需模型时，不得发送
任何抽样、对照或评审请求。评测费用始终单独展示，不混入线上请求的完整成本或成本目标。
持久日志同样不得记录视觉描述或 Upstream 响应正文；视觉诊断只记录有界状态元数据和不透明
trace/call ID。

### Agent 工具任务评测

代理只观察客户端实际执行的工具流程，不替客户端执行工具。完整轨迹为：用户任务 → 候选模型工具调用 →
客户端工具结果 → 候选模型最终回答。基线模型获得同一份真实工具结果，但评测请求不携带工具定义，基线只能
输出参考结论；评审器再结合完整轨迹盲评候选与基线。

有 Session ID 时，系统使用现有 HMAC Session Key 跨请求合并轨迹；没有 Session ID 时，只接受当前请求已经
包含的完整会话历史，不推测缺失轮次。Anthropic 必须返回 `stop_reason=end_turn`，Chat Completions 必须返回
`finish_reason=stop`，Responses 必须完成且不再发起函数调用，才会进入质量评测。30 分钟未结束、服务重启中断、
高风险或轨迹截断只保留审计。一次任务内从候选升级到强基线的两模型轨迹会保留有序模型路径和升级原因，并可作为
候选输出与最终基线输出的对照证据；包含多次或无法确定语义的模型切换仍不进入成对质量评测。
成本按每次物理调用累计，同一模型重试不会合并；形成质量证据时，最终输出只使用该模型所在尝试的成本与延迟，
不会把升级前候选失败的费用错误归到强基线。

每条完整轨迹只在首次完成时评测一次，不提供重新评测 API；完成请求使用随轨迹保存 7 天的摘要去重，重启后的
重复请求也不会再次入队，管理员删除轨迹时会同时删除摘要。服务不会持久化上游凭据，因此历史记录不能脱离
原请求安全重放；评测失败或重启中断时保留明确状态，由后续新任务继续积累证据。

## 10. Policy 即时发布与热加载

一个 Profile 只有一个 Active Policy 指针，没有 Draft、Ready、Canary 或待发布状态。每次保存携带
`expected_runtime_revision`，服务端按顺序完成完整校验、Runtime 预构建、SQLite CAS 事务和不可失败的 Registry
指针交换。成功响应表示所有后续新请求已经使用新 Policy；在途请求继续固定原快照。

每次保存、严格回滚或紧急下线都创建不可变版本。回滚不是重新激活旧记录，而是用当前 Profile、模型状态和能力
重新验证历史内容，兼容后复制成新的 Active；任何引用模型缺失、下线、退役或能力不足都会返回
`rollback_incompatible`，数据库 revision 和线上 Runtime 保持不变。

模型紧急下线会在同一发布事务里写入派生 Policy、把模型标记为 `offline`、清除相关 Session 并切换 Runtime。
已经发往上游的请求允许完成，之后的 `model=auto` 和显式模型请求都会立即观察新状态。`retired` 是保留历史引用的
永久墓碑，模型 ID 不能重新添加。

后台的配置估算使用通过 Route 硬门槛的候选：取所有 Route 的最低质量、最低稳定性和最高严重错误率，按
`质量 × 70% + 稳定性 × 15% + (100% - 严重错误率) × 15%` 计算展示分，再给出 A/B/C/D。任一 Route 没有达标
候选时为 D。该等级不参与运行时放行，也不能替代后续评测证据。

## 11. 上下文窗口与 Agent 配置

- `context_window` 是模型真实支持的上下文容量。
- `client_context_window` 是代理为 Agent 生成配置时使用的保守容量，已经扣除输出、工具、视觉
  描述和协议开销预留。

代理负责提供正确参数，但不会擅自压缩、截断或总结用户上下文；具体压缩仍由 Agent 完成。

## 12. 第一版边界

第一版保持简单：

- 单进程、单副本部署，配置、策略和统计使用 SQLite。
- Profile 是永久隔离边界；每个 Profile 只配置一个 Upstream，网关内部节点容错不属于本项目。
- 不持久化密钥、原始提示词、图片或完整回答。
- 不做分布式协调、不自动发布策略，也不引入强化学习或在线 Bandit。

这些限制是当前版本的明确范围。未来如果扩展到多副本，必须
先引入共享控制面、分布式预算和一致的策略发布机制，而不是共享挂载同一个 SQLite 文件。

## 13. 实施状态

1. **可用路由（已实现）**：`auto`、轻量任务分析、强模型基线、视觉计划、统一尝试预算、
   ClientCommit 前的计划内模型切换和结构化路由轨迹。
2. **稳定运行（已实现）**：Session 绑定、路由轨迹、不可变 Policy、Runtime revision CAS、严格回滚、
   模型紧急下线和原子热加载已上线。
3. **持续优化（已实现）**：异步抽样评测、盲化质量评审和证据候选；代理只负责同一 Upstream 的
   有限重试和模型切换，网关负责负载均衡、健康检查、熔断和节点故障转移。
4. **视觉生命周期（已实现）**：入口操作感知解析/改写、来源与传输兼容过滤，
   以及主回答前临时视觉故障的同一 Upstream 重试和模型回退。
5. **完整调用图（已实现）**：预先展开最坏调用图，为跨视觉、切换和回答的复合尝试提供原子预算
   预留，并把每次真实调用与 usage 成本关联到同一条路由轨迹。
6. **多轮混合路由（已实现）**：首轮任务判断、任务回合复用、会话/缓存门槛模型锁、三协议模型主动升级，
   以及有效升级、无效升级和漏升的异步校准。

每一阶段都必须用故障注入、成本核算和协议流式测试验证，不能仅以页面配置完成作为验收。
